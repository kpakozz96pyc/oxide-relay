# Руководство для агентов OxideRelay

## Область действия и источники истины

- Прочитайте [readme.md](readme.md) перед изменениями, которые затрагивают поведение продукта,
  конфигурацию, использование API, развертывание, разрешения или версионирование.
- Прочитайте [deploy/OPERATIONS.md](deploy/OPERATIONS.md), чтобы понять bootstrap, runtime,
  безопасность и поведение релизов.
- Прочитайте [docs/frontend-style-guide.md](docs/frontend-style-guide.md) перед
  изменениями во frontend UI или CSS. Переиспользуйте его токены и уже
  существующие компоненты.
- Считайте код, миграции и документ OpenAPI источником истины реализации.
  Обновляйте документацию, когда намеренное изменение реализации
  затрагивает задокументированное утверждение.

## Границы продукта

- OxideRelay — это лёгкий self-hosted сервер для хранения и доставки
  локализаций.
- Доступ использует глобальные прямые разрешения, членство в проекте и
  переопределение владельцем проекта. Не вводите и не подразумевайте роли,
  шаблоны ролей или permissions на уровне проекта.
- Не добавляйте API keys, audit logs, SMTP, MCP, workflow'ы ревью/статусов
  переводов или backend-возможности исключительно ради декоративного UI.
- Сохраняйте совместимость delivery URL и идентификаторов на основе путей с
  задокументированными правилами их валидации.

## Правила реализации

- Сохраняйте существующий frontend-стек React, TypeScript, React Router,
  TanStack Query, Lucide и custom CSS. Не добавляйте UI-библиотеки без
  явной потребности продукта.
- Вопрос custom-CSS-vs-component-library решён: OxideRelay остаётся на
  custom CSS без UI component library. Это относится к каждому экрану,
  включая translation grid — не вводите MUI, MUI DataGrid или любой
  другой UI kit для решения проблем grid, table или data density. Решайте их
  через существующие шаблоны таблиц, server-side pagination и токены из
  `docs/frontend-style-guide.md`.
- Сохраняйте поведение аутентификации и разрешений, если только задача явно
  не требует согласованного изменения.
- Предпочитайте существующие API calls, паттерны invalidation запросов и общие
  стили UI вместо дублирования flow или хардкода данных.
- Не добавляйте фейковые даты, пользователей, счётчики, activity или placeholder domain data.
- Сохраняйте адаптивность frontend и не меняйте общую левую навигацию,
  если только задача явно не включает это.
- Изменения backend должны быть минимальными, обновляйте OpenAPI при
  изменении public API и добавляйте или обновляйте тесты в существующем
  стиле проекта.

## Политика данных и версий

- Текущая версия проекта — `0.0.9`, и это разработка до `0.1.0`.
- До `0.1.0` разрешены ломающие миграции, а данные разработки считаются disposable.
- Начиная с `0.1.0`, используйте только forward-only migrations и не
  переписывайте историю миграций.

## Проверка и Git

- Для backend-изменений запускайте `cargo test` из корня репозитория.
- Для frontend-изменений запускайте `npm test -- --run` и `npm run build` из
  `frontend/`.
- Запускайте `git diff --check` перед commit. Запускайте проверки deployment configuration
  при изменении Docker- или Compose-файлов.
- Никогда не откатывайте и не stage'ьте несвязанные пользовательские изменения. Спрашивайте перед
  разрешением неоднозначного dirty worktree.
- Не делайте commit или push, если пользователь явно не просит об этом,
  кроме случаев, когда пользователь вызывает workflow `checkandcommit`.

## Навыки репозитория

- Локальный для репозитория marketplace Codex находится в `codex-marketplace/`. Зарегистрируйте
  его командой `codex plugin marketplace add ./codex-marketplace`, затем установите
  workflow через `codex plugin add checkandcommit@oxiderelay`.
- `/checkandcommit` запускает релевантные проверки, проверяет согласованность документации,
  запрашивает подтверждение перед исправлениями документации и делает commit только
  проверенных изменений. Он никогда не делает push автоматически.

## Work items в Plane

- Plane доступен через project-scoped MCP server `plane`. Когда
  пользователь ссылается на work item `OXR-*` или backlog Plane, получайте work
  item через Plane MCP до планирования или изменения кода.
- Считайте Plane инструментом координации задач, а не источником истины
  реализации. Сверяйте его требования с этим руководством и репозиторием
  перед правками.
- Читать Plane допустимо, когда это нужно для контекста задачи. Создавайте,
  обновляйте, комментируйте, переводите по статусам или удаляйте данные Plane
  только когда пользователь явно запрашивает эту мутацию, и сообщайте о
  произошедшем изменении.
