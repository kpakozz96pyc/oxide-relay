# Руководство по стилю frontend OxideRelay

## Назначение

Этот документ определяет текущий визуальный язык frontend OxideRelay и должен использоваться как основа для дальнейшей работы над UI.

Главный эталон - компактная таблица пользователей на странице `Users and permissions`:

- компактная высота строк
- преимущественно монохромное первое визуальное впечатление
- приглушённые поверхности на тёмном фоне
- сдержанные границы
- моноширинная типографика
- высокая и понятная плотность информации без визуального шума dashboard

Это руководство документирует уже существующий в кодовой базе стиль и уточняет предпочтительные паттерны для дальнейшей работы.

## Решение по frontend-библиотекам

OxideRelay остаётся на собственном CSS без библиотеки UI-компонентов: без MUI, MUI DataGrid, Bootstrap и других design-system framework. Это окончательное решение, распространяющееся на все экраны, включая насыщенные данными представления вроде таблицы переводов. Плотность таблиц, клавиатурная навигация и пагинация реализуются с помощью существующих табличных паттернов и приведённых ниже токенов, а не внедрением библиотеки grid-компонентов. Не следует возвращаться к этому вопросу без явной продуктовой необходимости; если она появится, для перехода потребуется отдельная migration epic, а не постепенное добавление библиотеки.

## Основные визуальные принципы

1. В первую очередь интерфейс должен быть тёмным и похожим на консоль.
2. Моноширинная типографика - основной голос продукта.
3. Большая часть UI строится на белом и сером цветах.
4. Тёплый оттенок допустим только как деликатная обработка поверхности, а не как доминирующий акцент.
5. Оранжевый - вспомогательный цвет акцента и фокуса, но не цвет обрамления.
6. Плотные и читаемые макеты предпочтительнее чрезмерных отступов, характерных для dashboard.
7. Карточки, таблицы и формы должны выглядеть как рабочий production-интерфейс, а не как макет.

#### Обработка тёплых поверхностей

Тёплый оттенок допустим только как деликатная примесь к тёмным поверхностям.

Текущие тёплые поверхности рабочих областей формируются из:

- `color-mix(in srgb, #fff8f1 6%, var(--surface-raised) 94%)`
- `color-mix(in srgb, #fff8ef 5% to 6%, var(--surface-hover or --surface-raised) 94% to 95%)`

Эти значения допустимы для:

- панелей рабочей области
- вложенных административных карточек
- ненавязчивых поверхностей настроек проекта и пользователя

Эти значения не предназначены для:

- разделителей вкладок
- крупных рамок таблиц
- активных состояний основной навигации
- глобального обрамления страницы

#### Правила использования цвета

1. По умолчанию UI должен производить монохромное впечатление.
2. Белый и серый должны формировать структуру раньше акцентных цветов.
3. Оранжевый должен появляться преимущественно в:
   - состояниях фокуса
   - тексте предупреждений и подсказок
   - деликатных тёплых смесях поверхностей
   - вспомогательных состояниях доставки, импорта и предупреждений
4. Границы карточек, панелей и таблиц по умолчанию должны оставаться нейтральными и не использовать оранжевое обрамление.
5. Активные вкладки, выделение строк таблицы и разделители макета должны использовать нейтральные белые и серые оттенки.
6. Новые необработанные цвета нельзя добавлять, пока они не оформлены как токены в `styles.css` и не внесены в этот документ.

4. `--text-sm` должен использоваться для большей части вторичного рабочего текста.
5. `--text-xs` предназначен только для структурного микротекста, но не для основного содержимого.

### Отступы

#### Шкала отступов

| Токен | Значение | Применение |
| --- | --- | --- |
| `--space-1` | `4px` | минимальные промежутки, корректировка padding у badges |
| `--space-2` | `8px` | плотное разделение подписи и поля, компактные промежутки строк |
| `--space-3` | `10px` | плотные компоненты, компактные карточки и строки |
| `--space-4` | `14px` | стандартный внутренний отступ |
| `--space-5` | `18px` | средний ритм карточек |
| `--space-6` | `22px` | padding панелей и промежутки блоков страницы |
| `--space-8` | `32px` | увеличенные промежутки макета |
| `--space-9` | `36px` | увеличенный padding панелей и форм аутентификации |
| `--space-10` | `40px` | отступы hero-блоков и оболочки |
| `--space-12` | `48px` | очень крупные отступы верхнего уровня, применять редко |

#### Правила отступов

1. Стандартные отступы содержимого должны строиться преимущественно на `--space-3`, `--space-4` и `--space-6`.
2. Плотные рабочие интерфейсы должны предпочитать `--space-2`, `--space-3` и `--space-4`.
3. `--space-8` и более крупные значения предназначены для оболочки, hero-блоков и разделения крупных секций.
4. Не вводите произвольные значения в пикселях, если подходящий токен уже существует.
5. Поля ввода, компактные таблицы и инспекторы должны тяготеть к плотной части шкалы.

#### Тени

| Токен | Значение | Применение |
| --- | --- | --- |
| `--shadow-sm` | `0 2px 8px rgba(0, 0, 0, 0.25)` | небольшие приподнятые элементы |
| `--shadow-card` | `0 4px 16px rgba(0, 0, 0, 0.20)` | стандартные карточки и панели |

#### Правила радиусов и теней

1. Почти всегда используйте `--radius-sm` и `--radius-md`.
2. Используйте только существующие тени панелей и карточек.
3. Не добавляйте декоративные наборы свечений.
4. `--shadow-panel` предназначен для заметных поверхностей аутентификации, а не для обычных панелей рабочей области.

### Анимация

#### Токены анимации

| Токен | Значение | Применение |
| --- | --- | --- |
| `--dur-fast` | `120ms` | реакция hover и focus |
| `--dur-base` | `200ms` | стандартные переходы UI |
| `--dur-slow` | `340ms` | появление страницы и крупные анимации раскрытия |
| `--ease-out` | `cubic-bezier(0.22, 1, 0.36, 1)` | стандартная функция плавности |

#### Правила анимации

1. Анимация должна повышать понятность, а не служить украшением.
2. Используйте существующие короткие переходы для hover, focus и появления.
3. Не накладывайте несколько анимаций на один компонент.
4. Анимация загрузки и прогресса должна оставаться деликатной и утилитарной.

## Структура страницы

### Оболочка приложения

- Левая навигация должна оставаться визуально стабильной между страницами.
- Основное содержимое использует существующий `content-shell`.
- Каждая страница рабочей области должна начинаться с:
  - надзаголовка
  - заголовка страницы
  - необязательных вспомогательных метаданных

### Предпочтительный паттерн рабочей области

Предпочтительная структура административных страниц и рабочих областей:

1. Заголовок
2. Toolbar или строка вкладок
3. Одна или несколько панелей
4. Плотные области содержимого внутри панелей

### Двухколоночный паттерн рабочей области

Для страниц настроек и административных деталей:

- слева: список, таблица или основная форма
- справа: детали, метаданные или инспектор
- рекомендуемое визуальное соотношение:
  - `1:2` для master-detail
  - примерно `1.5:1` для формы настроек и метаданных

## Панели и поверхности

### Стандартная панель

- Используйте `.panel`.
- Граница должна оставаться деликатной.
- Фон должен быть тёмным или тёмным с мягким тёплым оттенком.

### Тёплая панель рабочей области

Используется на страницах проектов и пользователей:

- тёплый почти белый оттенок, смешанный с тёмной поверхностью
- небольшое визуальное поднятие
- без агрессивного оранжевого контура

Сейчас это лучший вариант панели для экранов администрирования продукта; он должен стать стандартом для подобных страниц.

### Вложенные карточки

Вложенные карточки, например элементы ресурсов, группы разрешений и опасные зоны, должны:

- оставаться темнее внешней панели
- использовать сдержанные границы
- не полагаться на яркие акценты для формирования структуры

## Таблицы

Таблица пользователей - канонический стиль таблиц.

### Обязательные характеристики

- компактный вертикальный ритм
- приглушённые заголовки в верхнем регистре
- деликатная линия под заголовком
- тёмное заполненное тело таблицы
- выбранная строка обозначается левой линией и небольшим изменением фона
- без заметного чередования фона строк
- без избыточной hover-анимации

### Правила содержимого таблиц

- основная строка ячейки: жирная, короткая и контрастная
- дополнительная строка: приглушённая и меньшего размера
- числовые столбцы должны оставаться визуально спокойными
- badges не должны доминировать в строке

### Запрещено

- делать строки высокими без реальной необходимости содержимого
- использовать яркие акцентные границы по всей таблице
- добавлять декоративные цветовые блоки внутри ячеек

## Вкладки

Вкладки используются в настройках проекта и инспекторе пользователя.

Правила:

- активное состояние должно быть монохромным или почти монохромным
- для выделения используйте подчёркивание или нижнюю границу
- разделители вокруг вкладок должны быть нейтральными, а не акцентными
- строки вкладок должны восприниматься как структура, а не украшение

## Формы

### Поля ввода

- тёмный приподнятый фон
- деликатная граница
- оранжевая обработка кольца или границы фокуса
- placeholder остаётся приглушённым
- padding элементов управления по умолчанию должен быть компактным; избегайте чрезмерно крупных полей в административных workflow

### Макет формы

- располагайте поля вертикально, если нет веской причины для двухколоночной формы
- строки с несколькими полями должны использовать существующие grid-токены
- вспомогательный текст должен быть небольшим и вторичным

### Операции изменения

- основное действие сохранения: белая кнопка
- вторичное действие: ghost- или secondary-кнопка
- опасное действие: ghost danger-кнопка с визуальным отделением

## Кнопки

### Основная

- белая заливка
- чёрный текст
- предназначена для главного действия раздела

### Вторичная

- приглушённая приподнятая поверхность
- нейтральная граница

### Ghost

- прозрачная или почти прозрачная
- нейтральная граница

### Опасная

- только для разрушительных действий
- не должна располагаться вплотную к обычным действиям сохранения без пространственного разделения

## Обратная связь

### Баннеры

- используйте только существующие семантические баннеры
- success, warning, error, info
- текст должен быть коротким и рабочим

### Загрузка

- UI загрузки должен быть компактным
- избегайте крупных пустых оболочек, если не заблокирована вся страница

## Тексты и тон

- краткий
- рабочий
- без избыточного маркетинга
- без вымышленных данных
- без терминологии ролей там, где ролей не существует

## Адаптивность

- на обычных административных страницах не должно быть горизонтального overflow
- на узких экранах двухколоночные страницы складываются в одну колонку
- при необходимости таблицы могут прокручиваться горизонтально, но формы и панели должны сначала перестраиваться

## Правила реализации

1. Предпочитайте переиспользуемые классы в `styles.css` inline-стилям.
2. Не добавляйте единичные визуальные значения, если подходящий токен уже существует.
3. Если паттерн повторяется, предпочитайте общие utility- или component-классы локальным стилям страницы.
4. Новые страницы должны переиспользовать:
   - `.panel`
   - `.toolbar`
   - `.table-shell`
   - `.badge`
   - `.banner`
   - `.project-tab`
5. Не вводите новое визуальное направление отдельно для каждой страницы.

## Текущее соответствие

### Хорошее соответствие

- Таблица и инспектор пользователей
- Структура страницы настроек проекта
- Карточки ресурсов и строки метаданных
- Общие элементы форм и кнопки

### Частичное соответствие

- Страница проектов: структура корректна, но визуально она старше и хуже соответствует более плотному административному паттерну
- Страницы входа и сброса пароля: согласованы по палитре и типографике, но слишком сильно полагаются на inline-стили макета
- Оболочка приложения: в целом согласована, но часть композиции всё ещё жёстко задана inline

### Основные текущие отклонения

1. Inline-стили всё ещё используются на страницах макета и аутентификации.
2. Тёплая обработка панелей рабочей области дублируется на отдельных страницах вместо общего паттерна.
3. Страница проектов всё ещё использует старую композицию «панель создания + карточки проектов», которая визуально свободнее новых страниц рабочих областей.
4. Некоторые hover- и вспомогательные состояния теплее, чем требуется преимущественно монохромному UI.
5. Общие паттерны отступов и композиции заголовков не полностью выделены в переиспользуемые классы.
