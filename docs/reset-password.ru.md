# План сброса пароля

## Цель

Добавить поток генерации ссылки для сброса пароля администратором без доставки по email.

Текущее требуемое поведение:

- Пользователь с правами администратора может сгенерировать ссылку сброса для любого пользователя.
- Сгенерированная ссылка показывается в веб-интерфейсе ровно один раз.
- Ссылка остаётся действительной 15 минут.
- Интеграция с email или SMTP не используется.

## Область

Этот план охватывает полный поток, необходимый для того, чтобы сгенерированная ссылка была полезной:

1. Администратор генерирует одноразовую ссылку сброса для выбранного пользователя.
2. Admin UI показывает ссылку только в состоянии ответа на успешную мутацию.
3. Ссылка открывает публичную страницу `reset-password`.
4. Целевой пользователь задаёт новый пароль через эту страницу.
5. Токен становится непригодным к использованию после успешного сброса или истечения срока действия.
6. Существующие сессии этого пользователя инвалидируются после сброса пароля.

## Проектные решения

### Модель разрешений

Использовать существующее разрешение `ManageUsers` для генерации ссылок сброса.

Обоснование:

- То же разрешение уже позволяет создавать, обновлять, деактивировать и удалять пользователей.
- Генерация ссылки для сброса пароля по сути эквивалентна привилегированному управлению пользователями.
- Это позволяет не расширять каталог разрешений в первой итерации.

Если позже понадобится более строгая изоляция, это можно выделить в отдельное разрешение, например `ResetUserPasswords`.

### Хранение токенов

Добавить новую таблицу:

- `password_reset_tokens`

Предлагаемые столбцы:

- `id TEXT PRIMARY KEY`
- `user_id TEXT NOT NULL`
- `token_hash TEXT NOT NULL UNIQUE`
- `expires_at TEXT NOT NULL`
- `used_at TEXT NULL`
- `created_at TEXT NOT NULL`
- `created_by_user_id TEXT NOT NULL`

Примечания:

- Хранить только хэш исходного токена, а не сам исходный токен.
- Исходный токен должен существовать только в памяти во время формирования ответа.
- `created_by_user_id` даёт базовую аудируемость без построения полноценной системы audit log.

### Время жизни токена

- TTL: ровно 15 минут.

Правило реализации:

- `expires_at = now + 15 minutes`

### Одноразовая видимость в Admin UI

Бэкенд возвращает полный URL сброса только в успешном ответе на генерацию.

Фронтенд:

- хранит его только в состоянии компонента
- отображает его один раз в отдельной панели успеха
- очищает его при выборе другого пользователя, при генерации новой ссылки или при перезагрузке страницы/переходе

Это удовлетворяет требованию «показывается в веб-интерфейсе один раз», не делая вид, что бэкенд может контролировать, скопировал ли человек эту ссылку.

### Один активный токен на пользователя

Когда для пользователя генерируется новая ссылка сброса:

- сначала удалить или инвалидировать все существующие неиспользованные токены этого пользователя

Обоснование:

- более простая операционная модель
- меньше путаницы относительно того, какая ссылка является текущей
- более строгая безопасность

### Инвалидация сессий

После успешного сброса пароля:

- удалить все существующие сессии этого пользователя из `sessions`

Обоснование:

- это не позволяет старым аутентифицированным сессиям пережить сброс учётных данных

## Изменения на бэкенде

### 1. Миграция базы данных

Добавить новый файл миграции, например:

- `migrations/0002_password_reset_tokens.sql`

Ответственность схемы:

- создать `password_reset_tokens`
- добавить внешние ключи на `users(id)` и `users(id)` для `created_by_user_id`
- добавить индексы для поиска и очистки

Рекомендуемые индексы:

- `idx_password_reset_tokens_user_id`
- `idx_password_reset_tokens_expires_at`

### 2. Слой репозитория

Добавить новый модуль репозитория:

- `backend/src/repository/password_resets.rs`

Функции, которые нужно добавить:

- `create_reset_token(...)`
- `invalidate_active_tokens_for_user(...)`
- `find_active_token_by_hash(...)`
- `mark_token_used(...)`
- `purge_expired_tokens(...)`
- `delete_sessions_for_user(...)` или переиспользовать helper из репозитория сессий

Ожидаемая ответственность:

- хэшировать исходный токен перед вставкой
- получать только активные, неиспользованные и неистёкшие токены
- сохранять транзакционность записей в БД при завершении сброса

### 3. Утилиты токенов

Расширить `backend/src/util.rs` helper-функциями для:

- генерации случайного токена сброса
- хэширования токена для хранения

Предлагаемый подход:

- случайный токен длиной 32 байта
- кодирование через URL-safe base64 или hex
- хэширование через SHA-256 для хранения в БД

Важно:

- не переиспользовать Argon2-хэширование паролей для lookup-токенов
- для поиска токена требуется детерминированное хэширование

### 4. Admin API: генерация ссылки

Добавить новый аутентифицированный admin endpoint:

- `POST /api/v1/users/{id}/password-reset-link`

Поведение:

- требовать аутентифицированного пользователя
- требовать `ManageUsers`
- валидировать, что целевой пользователь существует и активен
- инвалидировать все предыдущие активные токены сброса для этого пользователя
- создать новый токен с TTL 15 минут
- вернуть payload, содержащий абсолютный или относительный URL сброса и timestamp истечения срока действия

Предлагаемый ответ:

```json
{
  "reset_url": "/reset-password?token=...",
  "expires_at": "2026-06-30T12:34:56Z"
}
```

Правило валидации:

- неактивные пользователи должны отклоняться с ошибкой валидации или конфликта

### 5. Public API: использование ссылки

Добавить новый публичный endpoint:

- `POST /api/v1/auth/reset-password`

Тело запроса:

```json
{
  "token": "...",
  "password": "new-password"
}
```

Поведение:

- валидировать новый пароль существующей password policy
- хэшировать входящий токен
- разрешать активный токен по хэшу
- отклонять истёкшие или уже использованные токены
- обновлять `users.password_hash`
- помечать токен как использованный
- удалять все сессии этого пользователя

Ответ:

- `204 No Content`

Поведение ошибок:

- неверный, истёкший или уже использованный токен должен возвращать одну и ту же обобщённую ошибку в стиле ошибок валидации

### 6. Роутер и OpenAPI

Обновить:

- `backend/src/http/mod.rs`
- `backend/src/http/docs.rs`

Необходимые изменения:

- зарегистрировать новый admin endpoint
- зарегистрировать новый публичный endpoint сброса
- добавить схемы запроса/ответа в OpenAPI

## UX-примечания

### UX администратора

Рекомендуемое поведение на `UsersPage`:

- подпись кнопки должна явно показывать привилегию, например `Generate reset link`
- панель успеха должна предупреждать, что ссылка показывается только один раз и истекает через 15 минут
- UI должен побуждать к немедленному копированию/открытию

### UX пользователя

Страница сброса должна:

- не требовать аутентификации
- явно показывать состояния истечения срока действия/ошибки
- давать простой путь возврата к администратору, если токен неверный или истёк

## Примечания по безопасности

1. Хранить в базе данных только хэши токенов.
2. Делать срок действия ссылок 15 минут.
3. Сделать токены одноразовыми.
4. Инвалидировать предыдущие активные токены того же пользователя.
5. Инвалидировать все пользовательские сессии после успешного сброса.
6. Возвращать обобщённые ошибки для неверных/истёкших/использованных токенов.
7. Логировать создание ссылки сброса и успешный сброс, не логируя исходные токены.

## Вне области

В этой итерации не добавлять:

- SMTP или любую доставку по email
- self-service запрос на forgot-password по email
- подсистему audit log
- отдельное разрешение для password reset
- rate limiting
- CSRF hardening сверх текущей модели приложения
- многошаговый поток подтверждения администратором

## Открытые вопросы

1. Должны ли ссылки сброса быть разрешены для неактивных пользователей?
   Рекомендация: нет.

2. Должен ли ответ возвращать абсолютный URL или относительный путь?
   Рекомендация: относительный путь от бэкенда, фронтенд может отрисовать его относительно текущего origin.

3. Должны ли администраторы иметь возможность генерировать ссылку сброса для самих себя?
   Рекомендация: да, если у них есть `ManageUsers`, чтобы поведение оставалось простым и симметричным.
