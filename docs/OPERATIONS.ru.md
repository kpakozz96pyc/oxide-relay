# Регламент эксплуатации

## Начальная инициализация

Поток запуска backend-сервиса выглядит так:

1. Загрузить конфигурацию из CLI, окружения, файла конфигурации и значений по умолчанию.
2. Открыть или создать файл базы данных SQLite.
3. Автоматически выполнить SQLx-миграции.
4. Заполнить неизменяемый каталог разрешений.
5. Создать первоначального администратора только тогда, когда таблица `users` пуста.

Учётные данные bootstrap-администратора требуются только для случая с пустой базой данных:

```text
OXIDERELAY_ADMIN_EMAIL
OXIDERELAY_ADMIN_PASSWORD
```

Если уже существует хотя бы один пользователь, сервис запускается без этих переменных.

Файл `.env.example` намеренно поставляется с этими двумя переменными закомментированными/пустыми — пустое или неустановленное значение трактуется как «не настроено», а не как реальные учётные данные.
Если база данных пуста и любая из переменных отсутствует или пуста, запуск немедленно завершается с понятной ошибкой, в которой названы обе переменные. Email обрезается по краям, валидируется и приводится к нижнему регистру перед сохранением; пароль проходит ту же валидацию, что и при обычном создании пользователя, а значение-заглушка `change-me` явно отклоняется. После создания первоначального администратора обе переменные можно удалить из `.env`.

## Восстановление пароля офлайн

Если ни один администратор не может войти, backend-бинарник может сгенерировать одноразовую ссылку для сброса пароля без запуска HTTP-сервера. Укажите ему ту же существующую базу SQLite, что используется в развёртывании:

```bash
./target/release/oxiderelay-backend \
  --config backend/config.toml.example \
  password-reset-link --email admin@example.com
```

Для стандартного развёртывания через Compose запустите установленный бинарник во временном контейнере, подключённом к тому же data volume:

```bash
docker compose run --rm oxiderelay \
  oxiderelay password-reset-link --email admin@example.com
```

Команда использует обычный приоритет `--database-path`, `OXIDERELAY_DATABASE_PATH` и файла конфигурации. Она отказывается создавать отсутствующую базу данных, принимает только email активного пользователя и заменяет любую предыдущую неиспользованную ссылку для этого пользователя. Напечатанный URL является относительным к origin развёртывания и истекает через 15 минут. Не сохраняйте этот URL в истории shell, логах, тикетах или чате.

## Demo Seed (только для разработки)

Для локальной разработки и скриншотов backend-бинарник может создать demo-проект ("Demo Storefront") с примерами языков, namespaces и translations, принадлежащий существующему пользователю:

```bash
./target/release/oxiderelay-backend \
  --config backend/config.toml.example \
  demo-seed --owner-email admin@example.com
```

Как и `password-reset-link`, это использует обычный приоритет `--database-path`, `OXIDERELAY_DATABASE_PATH` и файла конфигурации и отказывается создавать отсутствующую базу данных — сначала штатно инициализируйте сервис, чтобы уже существовал хотя бы один пользователь. Команда завершится ошибкой, если проект с demo-slug (`demo-storefront`) уже существует; перед повторным заполнением удалите его через UI.

**Только для разработки.** Не запускайте это на production-базе данных — команда записывает реальные строки (проект, языки, namespaces и translations) без отдельного флага "demo" и без автоматической очистки. Когда закончите, удалите созданный проект через UI.

## Настройки сессии

Связанные настройки:

```text
OXIDERELAY_SESSION_COOKIE_NAME
OXIDERELAY_SESSION_TTL_HOURS
OXIDERELAY_SESSION_COOKIE_SECURE
```

Рекомендуемые значения:

```text
local development: cookie_secure=false
HTTPS production:  cookie_secure=true
```

## Доступ к delivery

Доступ к delivery управляется независимо от admin-сессий:

```text
OXIDERELAY_PUBLIC_DELIVERY_ENABLED=true
OXIDERELAY_DELIVERY_TOKEN=
```

По умолчанию REST и статическая delivery-выдача остаются публичными. Установите
`OXIDERELAY_PUBLIC_DELIVERY_ENABLED=false`, чтобы все delivery-маршруты возвращали `404`, сохранив доступными admin UI и management API.

Установите `OXIDERELAY_DELIVERY_TOKEN` в длинный случайный secret, чтобы требовать этот заголовок:

```http
Authorization: Bearer <token>
```

Токен одинаково защищает все проекты и окружения. Он загружается при старте, поэтому для ротации обновите secret, перезапустите сервис, а затем обновите каждый клиент. Не коммитьте токен и не помещайте его в URL. Используйте HTTPS, чтобы заголовок был зашифрован при передаче. Защищённые ответы используют приватное клиентское кеширование вместо общего публичного кеширования.

## Ограничение частоты входа

Неудачные попытки входа сохраняются в SQLite по хэшу нормализованного email-адреса. Один идентификатор может сделать 15 неуспешных попыток в течение пятиминутного окна. Дальнейшие попытки будут возвращать `429 RateLimited`, пока окно не истечёт. Успешные входы очищают счётчик. Это ограничение фиксировано в текущем MVP.

## Запуск через Docker

Предпочтительный путь установки:

```bash
cp .env.example .env
docker compose up -d
```

Если порт `8080` уже занят на хосте, измените `OXIDERELAY_PUBLISHED_PORT`
в `.env`. Сохраните `OXIDERELAY_PORT=8080`, чтобы приложение внутри контейнера продолжало слушать свой стандартный порт.

Сборка из исходников:

```bash
docker build -f deploy/Dockerfile -t oxiderelay:latest .
```

Запуск с постоянным хранилищем SQLite:

```bash
docker run \
  --name oxiderelay \
  --env-file .env \
  -p 8080:8080 \
  -v oxiderelay-data:/data \
  oxiderelay:latest
```

Файл SQLite должен находиться на доступном для записи volume, таком как `/data`.
Тот же контейнер обслуживает frontend по `/` и backend API по `/api`.

## Резервное копирование и восстановление

Стратегия резервного копирования для SQLite:

1. По возможности остановить поток записи.
2. Скопировать файл базы данных с постоянного volume.
3. Сохранить соответствующие файлы `-wal` и `-shm`, если они существуют во время живого копирования.

Пример:

```bash
cp /data/oxiderelay.sqlite /backups/oxiderelay-$(date +%F).sqlite
cp /data/oxiderelay.sqlite-wal /backups/ 2>/dev/null || true
cp /data/oxiderelay.sqlite-shm /backups/ 2>/dev/null || true
```

Стратегия восстановления:

1. Остановить сервис.
2. Заменить файлы базы данных SQLite в data volume.
3. Снова запустить сервис и при необходимости дать ему выполнить миграции.

## Политика схемы и обновлений

### Разработка до версии 0.0.9

OxideRelay находится в активной pre-`0.1.0` разработке. Схема базы данных и данные на этом этапе не совместимы между обновлениями. Используйте только одноразовые данные для разработки; после несовместимых изменений остановите сервис и пересоздайте базу данных SQLite.

### Релизы, начиная с версии 0.1.0

- Миграции выполняются автоматически при запуске.
- Запуск является частью поддерживаемого пути обновления.
- Релизы сохраняют существующие данные с помощью миграций только вперёд.
- Если миграция завершилась ошибкой, сервис следует считать неуспешно развёрнутым.

Рекомендуемый процесс обновления для `0.1.0` и новее:

1. Сделать резервную копию SQLite volume.
2. Развернуть новый backend-образ.
3. Следить за логами запуска до завершения миграций.
4. Выполнить smoke-проверку `'/api/health'` и одного аутентифицированного endpoint.

## Чек-лист релиза

Шаги для подготовки и публикации нового релиза OxideRelay по порядку:

1. Обновите версию в двух местах, где она объявлена:
   - `Cargo.toml` (`version = "x.y.z"`) — backend crate, ответ `/api/health` и версия документа OpenAPI автоматически берут её отсюда (`backend/src/http/docs.rs` читает её через `env!("CARGO_PKG_VERSION")`), поэтому на стороне backend больше ничего редактировать не нужно.
   - `frontend/package.json` (`"version"`) — синхронизируется с `Cargo.toml` job'ом CI `Version consistency`, который падает, если значения расходятся.
2. Запустите backend-тесты: `cargo test --locked`.
3. Запустите frontend-тесты и сборку: `cd frontend && npm test -- --run && npm run build`.
4. Убедитесь, что Docker-образ собирается из чистого checkout:
   `docker build -f deploy/Dockerfile -t oxiderelay:release-check .`
5. Выполните smoke-тест собранного образа: либо `bash scripts/smoke-compose.sh`,
   либо пройдите по чек-листу smoke-теста ниже для контейнера, запущенного из образа, собранного на шаге 4.
6. Проверьте `readme.md` и этот файл на устаревшие ссылки на версии, изменённые значения по умолчанию или переменные окружения, появившиеся с прошлого релиза.
7. Отправьте release tag: `git tag vX.Y.Z && git push origin vX.Y.Z`. Это
   запускает workflow
   [Publish release](../.github/workflows/docker-publish.yml),
   который собирает и публикует `kpakozz96pyc/oxiderelay:vX.Y.Z` (и `:latest` для стабильных тегов без pre-release), упаковывает нативный Linux-архив и создаёт GitHub Release с этим архивом во вложении.
8. Просмотрите и отредактируйте сгенерированные заметки к GitHub release: кратко опишите пользовательские изменения, сошлитесь на закрытые issues/PR и укажите всё, что связано с миграциями, согласно политике схемы и обновлений выше.

## Чек-лист smoke-теста

Для нового окружения:

1. Начните с пустого доступного для записи каталога данных.
2. Передайте bootstrap-учётные данные администратора.
3. Подтвердите, что `/api/health` возвращает `{"status":"ok","database":"ok","version":"0.0.9"}`.
4. Войдите под bootstrap-администратором.

Для существующего окружения:

1. Начните с существующего файла SQLite.
2. Не задавайте переменные bootstrap-администратора.
3. Подтвердите, что запуск проходит без bootstrap-ошибок.
4. Подтвердите, что существующий пользователь по-прежнему может пройти аутентификацию.

Для нового окружения с отсутствующими или отклоняемыми учётными данными (каждый случай должен завершать запуск с понятной ошибкой, а не с молча созданным администратором):

1. Начните с пустого доступного для записи каталога данных и без заданных переменных bootstrap-администратора.
2. Запустите с `OXIDERELAY_ADMIN_EMAIL`/`OXIDERELAY_ADMIN_PASSWORD`, установленными в пустые строки.
3. Запустите с `OXIDERELAY_ADMIN_PASSWORD=change-me`.
