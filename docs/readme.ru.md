# OxideRelay

**OxideRelay** - самостоятельно размещаемый инфраструктурный сервис локализации для централизованного хранения, управления и доставки переводов между приложениями.

Проект предназначен для команд, которые не хотят хранить переводы отдельно в каждом сервисе, веб-приложении или мобильном клиенте.

OxideRelay выступает единым источником истины для данных локализации, используемых frontend-, backend- и мобильными приложениями.

---

# Статус разработки

Текущая версия: `0.0.9`.

OxideRelay находится в активной разработке до выпуска `0.1.0`.

До `0.1.0` допускаются ломающие миграции, а данные разработки считаются одноразовыми.
Начиная с `0.1.0`, используйте только последовательные миграции вперёд и не переписывайте историю миграций.

# Зачем нужен OxideRelay?

Типичная структура локализации выглядит так:

```text
frontend
 └── locales/en.json
 └── locales/ru.json

backend
 └── resources/en.json
 └── resources/ru.json

mobile
 └── strings.xml
 └── Localizable.strings
```

Со временем переводы начинают дублироваться в нескольких приложениях и окружениях.

OxideRelay предлагает централизованный подход:

```text
                OxideRelay
                     │
      ┌──────────────┼──────────────┐
      │              │              │
Frontend         Backend        Mobile
```

Все приложения получают переводы из единого источника.

# Основные понятия

## Проект

Логическая группа переводов.

Примеры:

```text
HR Portal
Mobile App
Landing Site
Admin Panel
```

При создании нового проекта OxideRelay автоматически формирует начальную структуру:

* Namespace по умолчанию: `common`
* Окружения по умолчанию: `development`, `staging`, `production`
* Язык по умолчанию: `en` (`English`)

---

## Язык

Поддерживаемая локаль.

Примеры:

```text
en
ru
sr
de
```

---

## Namespace

Логическая группа ключей переводов внутри проекта.

Примеры:

```text
common
validation
checkout
profile
```

Ключи переводов внутри namespace хранят только локальную часть ключа.

Примеры:

```text
namespace: common
key: button.save

namespace: validation
key: required
```

---

## Окружение

Изолированная область переводов.

Примеры:

```text
Development
Staging
Production
```

---

## Проверка placeholders

Таблица переводов предупреждает, если в значении отсутствует placeholder, который используется в значении того же ключа на другом языке. Благодаря этому динамическое содержимое не теряется в переводе незаметно.

Распознаются два варианта синтаксиса:

```text
{{name}}
{name}
```

Оба варианта используют одинаковый набор символов в имени placeholder: буквы, цифры, `_` и `.`, например `{{user.first_name}}`. Проверка сравнивает набор имён placeholders во всех языках, где у ключа уже есть значение. Язык помечается только тогда, когда в нём отсутствует имя, используемое хотя бы в одном другом заполненном языке. Это неблокирующее предупреждение в ячейке таблицы, которое никогда не мешает сохранению.

---

## Проверка записи переводов

Backend применяет одинаковые правила проверки при создании и обновлении переводов, а также при импорте JSON:

* Ключи обрезаются по краям, не могут быть пустыми и ограничены 500 символами Unicode.
* Ключи локальны для выбранного namespace и не должны начинаться с `{namespace}.`.
* В ключах запрещены двоеточия, фигурные скобки и управляющие символы. Поддерживаются остальные печатные символы Unicode, точки, дефисы, подчёркивания и пробелы.
* Значения обрезаются по краям, не могут быть пустыми и ограничены 10 000 символами Unicode.
* Описание необязательно и ограничено 2 000 символами Unicode. Пустые описания и строки только из пробелов сохраняются как `null`.

Импорт JSON принимает плоский объект не более чем с 5 000 элементами. Перед записью проверяется весь пакет; если хотя бы один элемент некорректен, отклоняется весь пакет. Существующие значения для выбранных окружения, языка и namespace обновляются через upsert.

# Пользователи и разрешения

OxideRelay использует модель доступа на основе разрешений.

---

## Пользователь

У пользователя могут быть:

* Прямые разрешения
* Доступ к определённым проектам

Участники проекта с `ReadTranslations` могут читать переводы во всех окружениях.
Для записи во все окружения, кроме `production`, требуется `EditAll`, а для
`production` требуется `EditProd`.

В MVP нет отдельной таблицы участия в окружениях.

Прямые разрешения глобальны и не привязаны к проекту: `user_project_access` только определяет, к каким проектам применяются разрешения пользователя, и не содержит отдельного набора разрешений для каждого проекта. Назначение одному пользователю разных разрешений в разных проектах, например редактора в одном и только чтения в другом, не входит в MVP; этот вариант был рассмотрен и отклонён в OXR-76.

---

## Разрешения

### Управление пользователями

```text
ManageUsers
ManagePermissions
```

В MVP `ManagePermissions` позволяет назначать и удалять прямые разрешения пользователей.

Это разрешение не позволяет создавать новые коды разрешений во время выполнения.

### Безопасность администраторов

Система независимо контролирует, чтобы хотя бы один активный пользователь сохранял `ManageUsers` и хотя бы один активный пользователь сохранял `ManagePermissions`. Деактивация, удаление или снятие любого из этих разрешений у последнего активного обладателя блокируется, даже если у пользователя остаётся второе разрешение. Потерю последнего обладателя `ManagePermissions` нельзя исправить без прямого доступа к базе данных: bootstrap первоначального администратора выполняется только один раз для пустой таблицы `users`, а единственная recovery-команда CLI `password-reset-link` восстанавливает доступ к учётной записи, но не разрешения.

Самостоятельный отзыв собственных `ManageUsers` или `ManagePermissions` и изменение другого активного администратора разрешены, пока сохраняется описанный выше инвариант. Отдельного уровня администраторов и дополнительного разрешения нет. Перед отправкой любого изменения разрешений административный UI требует явного подтверждения независимо от затронутых разрешений.

Полный анализ политики приведён в OXR-75, реализация - в OXR-77.

### Восстановление пароля

Текущий процесс восстановления пароля инициируется администратором.

Правила:

```text
Пользователь с ManageUsers может создать ссылку сброса пароля для любого активного пользователя.
Ссылка показывается в административном UI один раз.
Ссылка действительна 15 минут.
В текущей реализации email не отправляется.
После успешного сброса пароля все существующие сессии пользователя аннулируются.
```

Ссылки сброса предназначены для операционного восстановления в самостоятельно размещаемых установках, где SMTP ещё не настроен.

Если ни один администратор не может войти, создайте ссылку непосредственно для существующей базы SQLite без запуска HTTP-сервера:

```bash
cargo run -p oxiderelay-backend -- \
  --config backend/config.toml.example \
  password-reset-link --email admin@example.com
```

Команда использует обычный приоритет конфигурации базы данных, требует уже существующий файл базы и выводит относительный URL `/reset-password`, действительный 15 минут. Перед открытием добавьте к URL origin развёртывания. Относитесь к выводу как к паролю: создание новой ссылки для того же пользователя аннулирует предыдущую.

# Доступ к проектам

Пользователи видят только явно назначенные им проекты.

Пример:

```text
John

Projects:
- HR Portal
- Mobile App
```

Доступ к проекту хранится отдельно от разрешений.

Владелец проекта автоматически добавляется в доступ к проекту и может выполнять в нём любые действия.

В MVP доступ владельца к проекту хранится в `user_project_access`.

Проектные разрешения и разрешения окружений владельца остаются неявными и не требуют глобального назначения.

John не может получить доступ к другим проектам системы.

---

# Владелец проекта

Создатель проекта автоматически становится его владельцем.

Владелец проекта может:

* Управлять участниками проекта
* Предоставлять доступ к проекту
* Управлять переводами проекта

Глобальные административные привилегии для этого не требуются.

В MVP это встроенное правило авторизации: внутри собственного проекта владелец считается обладателем всех проектных разрешений и разрешений окружений.

Для пользователей, не являющихся владельцами, управление участниками требует `ManageProjectMembers` в доступном им проекте.

---

# REST API

Доставка переводов для backend-приложений.

Эндпоинты доставки по умолчанию публичны и не используют аутентификацию административной сессии.
Их можно глобально отключить или защитить единым общим Bearer-токеном развёртывания.
Сгенерированный документ OpenAPI доступен по `GET /api/openapi.json`.

# Конфигурация времени выполнения

Приоритет конфигурации:

```text
Аргументы CLI
→ переменные окружения
→ config.toml
→ встроенные значения по умолчанию
```

Поддерживаемые параметры:

```text
OXIDERELAY_HOST
OXIDERELAY_PORT
OXIDERELAY_DATABASE_PATH
OXIDERELAY_FRONTEND_DIST_PATH
OXIDERELAY_SESSION_COOKIE_NAME
OXIDERELAY_SESSION_TTL_HOURS
OXIDERELAY_SESSION_COOKIE_SECURE
OXIDERELAY_PUBLIC_DELIVERY_ENABLED
OXIDERELAY_DELIVERY_TOKEN
OXIDERELAY_ADMIN_EMAIL
OXIDERELAY_ADMIN_PASSWORD
```

Настройки сессии по умолчанию:

```text
cookie_name = oxiderelay_session
ttl_hours = 168
cookie_secure = false
```

Для локальной разработки оставьте `cookie_secure=false`.

Для развёртываний с HTTPS установите `OXIDERELAY_SESSION_COOKIE_SECURE=true`.

Настройки доставки по умолчанию:

```text
public_delivery_enabled = true
delivery_token = unset
```

Установите `OXIDERELAY_PUBLIC_DELIVERY_ENABLED=false`, чтобы все REST- и статические эндпоинты доставки возвращали `404`. Административный UI и management API при этом не отключаются.

Установите непустой `OXIDERELAY_DELIVERY_TOKEN`, чтобы для всех запросов доставки требовался следующий заголовок:

```http
Authorization: Bearer <OXIDERELAY_DELIVERY_TOKEN>
```

Токен является единым общим секретом развёртывания, а не API-ключом или системой идентификации пользователей. При его использовании всегда применяйте HTTPS. Защищённые ответы используют приватное клиентское кеширование и зависят от заголовка `Authorization`.

### Ограничение частоты входа

Для защиты от перебора паролей попытки входа сохраняются в SQLite по хешу нормализованного email. Для каждого идентификатора допускается 15 неудачных попыток входа за пятиминутное окно. Последующие попытки возвращают `429 RateLimited` до завершения окна. Успешный вход очищает счётчик. API возвращает одинаковый ответ о неверных данных для неизвестной, неактивной учётной записи и неправильного пароля.

# Локальный запуск

Быстрый запуск для локальной разработки:

```bash
cargo run -p oxiderelay-backend -- --config backend/config.toml.example
```

```bash
cd frontend
npm install
npm run dev
```

Dev-сервер Vite проксирует `/api` и `/static` на backend по адресу `127.0.0.1:8080`.
Все поддерживаемые режимы, включая локальный production-подобный запуск, нативный бинарный файл, Docker Compose и сборку Docker из исходников, описаны ниже в разделе «Режимы запуска».

## Режимы запуска

OxideRelay поддерживает несколько режимов в зависимости от того, разрабатываете ли вы приложение, проверяете production-подобную установку или устанавливаете сервис для регулярного использования.

### 1. Режим разработки

Запустите backend и frontend отдельно:

```bash
cargo run -p oxiderelay-backend -- --config backend/config.toml.example
```

```bash
cd frontend
npm install
npm run dev
```

Используйте этот режим для активной разработки frontend или backend.

### 2. Локальный production-подобный режим

Один раз соберите frontend, затем запускайте только backend:

```bash
cd frontend
npm install
npm run build
```

```bash
cargo run -p oxiderelay-backend -- \
  --config backend/config.toml.example \
  --frontend-dist-path frontend/dist
```

Используйте этот режим для локальной проверки упакованного UI без Docker.

### 3. Нативный бинарный файл

Сначала соберите frontend, затем скомпилируйте и запустите backend:

```bash
cd frontend
npm install
npm run build
cd ..
```

```bash
cargo build --release -p oxiderelay-backend
./target/release/oxiderelay-backend \
  --config backend/config.toml.example \
  --frontend-dist-path frontend/dist
```

Этот режим полезен, если требуется нативный процесс вместо контейнера.
Готовые Linux-архивы релизов описаны ниже в разделе «Развёртывание».

### 4. Docker Compose

Рекомендуемый способ установки:

```bash
cp .env.example .env
# Отредактируйте .env и задайте данные первоначального администратора
docker compose up -d
```

Используется опубликованный image, а SQLite сохраняется в Docker volume.

### 5. Docker из исходников

Чтобы собрать image локально:

```bash
docker build -t oxiderelay:local .
docker run --rm -p 8080:8080 \
  -e OXIDERELAY_ADMIN_EMAIL=admin@example.com \
  -e OXIDERELAY_ADMIN_PASSWORD=change-me \
  oxiderelay:local
```

Используйте этот вариант, если требуется собственная локальная сборка image.

# Обзор API

OxideRelay поддерживает два способа доставки:

* Доставка locale bundle через REST для backend- и сервисных клиентов
* Доставка статических JSON-файлов для frontend-клиентов

---

# REST-доставка locale bundle

Рекомендуемый эндпоинт:

```http
GET /api/v1/projects/{project}/locales/{locale}?environment=production
```

Пример:

```http
GET /api/v1/projects/hr-portal/locales/ru?environment=production
```

Ответ:

```json
{
  "version": "2025-08-03T09:31:14.431Z",
  "translations": {
    "common.button.save": "Сохранить",
    "common.button.cancel": "Отмена"
  }
}
```

Правила:

```text
Ответ содержит переводы из всех namespaces.
Каждый ключ ответа имеет формат {namespace}.{key}.
Ключ в базе данных не содержит префикс namespace.
```

Ответы locale bundle содержат поле `version` и поддерживают `ETag` / `If-None-Match`.
При использовании URL с версией, например
`/api/v1/projects/hr-portal/locales/ru?environment=production&v=<version>`,
сервер проверяет, что `<version>` соответствует версии возвращаемого содержимого.
Только после этого ответ можно кешировать как immutable. Значение `v`, не соответствующее текущей версии, устаревшее после изменения перевода или просто некорректное, отклоняется с `404 Not Found`. Устаревший или поддельный URL с версией никогда не будет закеширован как immutable.

---

# Доставка статического JSON

Доставка переводов для frontend-приложений.

Эндпоинты статического JSON используют те же настройки публичной доставки и Bearer-токена, что и REST-эндпоинты.

Рекомендуемый процесс:

```http
GET /api/v1/projects/hr-portal/delivery-manifest/ru?environment=production
```

Manifest возвращает URL с версиями для locale bundle и каждого JSON-файла namespace.
Если настроен токен доставки, клиенты должны отправлять Bearer-заголовок как при получении manifest, так и при запросе каждого возвращённого им URL.

Пример:

```http
GET /static/hr-portal/production/ru/common.json?v=<version>
```

Ответ:

```json
{
  "button.save": "Сохранить",
  "button.cancel": "Отмена"
}
```

Статический JSON возвращает один namespace в каждом файле, поэтому ключи ответа не содержат префикс namespace.
Статические URL с версией используют долгосрочное immutable-кеширование браузера, но только если `v` совпадает с текущей версией файла namespace. При несовпадении `v` возвращается `404 Not Found`, а не кешируемое immutable-содержимое.
Статические URL без версии также работают и используют короткий TTL и заголовки ревалидации.

# Примеры запросов доставки

Практические примеры `curl` для каждого поддерживаемого режима доставки. Все эндпоинты доставки одинаково поддерживают перечисленные ниже режимы; для краткости показан только эндпоинт locale bundle.

**Публичный URL без версии** - конфигурация по умолчанию без токена. Короткоживущий кеш; выполняйте ревалидацию по возвращённому `ETag`:

```bash
curl -i "https://relay.example.com/api/v1/projects/hr-portal/locales/ru?environment=production"

# При следующем запросе выполните ревалидацию с ETag из первого ответа:
curl -i "https://relay.example.com/api/v1/projects/hr-portal/locales/ru?environment=production" \
  -H 'If-None-Match: "<etag-from-previous-response>"'
# -> 304 Not Modified, если ничего не изменилось
```

**Публичный URL с версией** - привязка к известной версии содержимого для immutable-кеширования.
Получите `<version>` из delivery manifest или поля `version` предыдущего ответа:

```bash
curl -i "https://relay.example.com/api/v1/projects/hr-portal/locales/ru?environment=production&v=<version>"
# -> 200 с "Cache-Control: public, max-age=31536000, immutable", если <version> актуальна
# -> 404 Not Found, если <version> устарела или некорректна
```

**Защита Bearer-токеном** - когда в развёртывании настроен `OXIDERELAY_DELIVERY_TOKEN`. Один и тот же заголовок требуется для каждого эндпоинта доставки, включая manifest и статические JSON-файлы:

```bash
curl -i "https://relay.example.com/api/v1/projects/hr-portal/locales/ru?environment=production" \
  -H "Authorization: Bearer <OXIDERELAY_DELIVERY_TOKEN>"
# -> 401 Unauthorized без заголовка, если настроен токен
# -> "Cache-Control: private, ..." и "Vary: Authorization" в защищённых ответах
```

# Модель безопасности

В MVP OxideRelay есть два класса доступности:

* Административный UI и management API используют сессионную аутентификацию и предназначены для доверенных операторов.
* Эндпоинты доставки не используют административные сессии; они публичны по умолчанию, могут быть глобально отключены или защищены единым общим Bearer-токеном:
  * Метаданные доставки: `/api/v1/projects/{project}/delivery-metadata`
  * REST-доставка locale bundle: `/api/v1/projects/{project}/locales/{locale}`
  * Delivery manifest: `/api/v1/projects/{project}/delivery-manifest/{locale}`
  * Доставка статического JSON: `/static/{project}/{environment}/{locale}/{namespace}.json`

Общий токен не имеет областей действия по проектам, идентификации клиентов, срока действия или управляемой сервером ротации. Считайте содержимое публичным, если токен не настроен и не передан только доверенным клиентам.

Приватные переводы нельзя выставлять в публичный интернет без HTTPS и либо общего токена доставки, либо защиты reverse proxy/VPN перед OxideRelay.

Рекомендуемые меры развёртывания:

* Предпочтительно запускать OxideRelay во внутренней сети или приватной подсети.
* Если требуется внешний доступ, включите токен доставки и TLS, разместите OxideRelay за reverse proxy с аутентификацией и TLS либо за VPN.
* Ограничьте входящий доступ firewall-правилами или security groups, чтобы сервис был доступен только доверенным пользователям и приложениям.

# Развёртывание

OxideRelay рассчитан на простую установку и эксплуатацию.

Рекомендуемый способ установки - Docker Compose:

```bash
cp .env.example .env
# Отредактируйте .env и задайте данные первоначального администратора
docker compose up -d
```

Стандартный [compose.yaml](../compose.yaml) использует опубликованный image
`kpakozz96pyc/oxiderelay:latest`, хранит данные SQLite в volume
`oxiderelay-data` и читает параметры времени выполнения из `.env`.

Каждая отправка git-тега `vX.Y.Z` публикует соответствующий image
`kpakozz96pyc/oxiderelay:vX.Y.Z`; стабильные релизы также обновляют `:latest`.
Для предсказуемых и воспроизводимых обновлений закрепляйте `OXIDERELAY_IMAGE`
в `.env` на теге релиза вместо `:latest`, поскольку `:latest` может измениться между развёртываниями.

### Нативный Linux-архив

Каждый тег релиза `vX.Y.Z` также публикует нативный Linux-архив. Для его запуска конечным пользователям не нужен Node.js.

Архив содержит:

* `./oxiderelay-backend`
* `./frontend/dist`
* `./backend/config.toml.example`

Из корня распакованного архива:

```bash
cp backend/config.toml.example config.toml
mkdir -p data
# Замените email и пароль bootstrap_admin в config.toml.
# Пароль из примера "change-me" намеренно отклоняется.
./oxiderelay-backend --config config.toml
```

Запускайте бинарный файл из корня архива, чтобы пути `./frontend/dist` и
`./data/oxiderelay.sqlite` разрешались правильно. После первого успешного запуска удалите данные bootstrap из `config.toml`: они нужны только для создания первоначального администратора в пустой базе.

Контейнер обслуживает административный UI по `/`, а API - по `/api`.
Другие варианты установки и запуска описаны выше в разделе «Режимы запуска».
